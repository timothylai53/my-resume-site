For the prototype, use reporting-oriented storage.

Do NOT store a full duplicate of every ~500 MB raw dataset in PostgreSQL for
each reporting period.

The backend should:

1. Accept the raw workbook.
2. Validate it.
3. Process it using Pandas/business rules.
4. Extract the fields required for reporting, dashboard filtering,
   drill-down, validation and historical comparison.
5. Store the processed reporting records in PostgreSQL.
6. Store processing-run/report-period metadata separately.

Create a processing_runs/reporting_period entity containing metadata such as:

- id
- report_start_date
- report_end_date
- original_filename
- uploaded_at
- record_count
- validation_status
- processing_status

Processed vulnerability records should reference the appropriate processing
run/reporting period.

Do not assume the application is permitted to permanently retain uploaded raw
workbooks.

For the university prototype, raw workbook retention should be temporary/local
unless a separate retention requirement is later confirmed.

Keep the architecture flexible so an approved raw-file storage/retention
mechanism can be added later without redesigning the reporting database.

Do not delete data required for:
- reporting
- dashboard filtering
- drill-down
- historical comparisons
- validation/audit traceability

The exact final reporting-column list can remain configurable while the
business rules and dashboard requirements are being completed.
