3. How are archive files combined and read?

The permanent design uses one folder combine, not one manually created query per archived file.

All four final Medium queries reference the shared qryMediumHistory query.

However, a shared query does not prove that each physical file is read only once per refresh. The supplied code does not establish a guaranteed shared cache or single materialised read across the four outputs.

Therefore:

Logical structure: one shared folder-history query.
Physical reads per refresh: not measured or guaranteed.
It would be inaccurate to claim either “exactly once” or “exactly once per Medium sheet” without observing refresh execution.
4. Where does the fixed Medium population come from?

It comes from the existing Medium baseline tables copied into the master workbook.

Those tables are read by the four _History queries. The manual workflow also describes a fixed identifier list in each Medium sheet.

It is not rebuilt from the archive folder.

The final queries use those baseline tables as the left side of their joins. Consequently:

Existing baseline records receive monthly snapshot values.
Records found only in current or archived raw data are not automatically appended to the Medium population.
The original upstream source of those baseline lists, before they were copied into the workbook, is not confirmed.
5. Which monthly fields are taken from raw data, and how are they created?

Each monthly snapshot retrieves:

Remediation Status
Remediation Domain
Remediation Planned Date
Final Severity Rating

Report End Date determines the snapshot label.

The creation method is:

Select the required source fields.
Clean the matching identifier.
Prepare one record per identifier.
Convert the planned date to a month label.
Left Outer merge into the baseline.
Expand the four snapshot fields into dated columns.

Archived reporting dates are processed using List.Accumulate. This is repeated merge-and-expand, not a Power Query pivot operation.

The Latest fields duplicate the current snapshot’s corresponding fields. The planning flags are then calculated from the Latest planned month.

Important structural detail: the supplied code does not refresh the baseline’s geography or other descriptive columns from current raw data. Those remain from the baseline unless another step updates them.

6. How is “keep the first match” implemented?

Your supplied code uses:

Plain Text
Table.Group by identifier
→ Table.First within each group
→ Table.ExpandRecordColumn

It does not use:

Table.Distinct
Table.FirstN after a merge
A latest-date or business-priority selection rule

It keeps the first record encountered in each identifier group. There is no explicit sorting rule to resolve conflicting duplicates.

8. Do formulas or PivotTables sit on query output that is overwritten?

The intended design keeps them separate:

Query output tables occupy dedicated data areas.
PivotTables sit on reporting sheets.
Rate/KPI/title formulas sit outside the query tables.
Historical baseline tables remain separate from automated output tables.

Query refresh replaces the contents of the output tables, not the separate report formulas.

The exact current placement has not been verified. In particular, the report-date helper must remain outside the existing Cluster mapping table and any area that another table or Pivot can expand into.

Also, a final Medium query must not load over its own baseline source table.
