Keep the existing three-report design:

2. Remediation Rate

Keep the existing:

- Corporate dashboard design
- Filters

Do NOT redesign the interface from scratch.

Apply the following refinements.

==================================================

==================================================

Keep:

optional and OFF by default.

P1
P2

Include Blank Priority

"562 vulnerabilities without Prioty are excluded from this view."

Do not hardcode 562.

Calculate the excluded count dynamically from the selected processing run and
current applicable filters.

==================================================
3. REMEDIATION RATE KPI CARDS
==================================================

Show:

Total Vulnerabilities
Met SLA
Breached SLA
Exception
Open
Overdue

Counts must respond to the currently selected filters.

If percentages are displayed, calculate them using the currently filtered
report population.

==================================================
4. REMEDIATION PLAN KPI CARDS
==================================================

Do NOT create one KPI card for every Quarter.

As reporting periods grow, this would make the dashboard cluttered.

Instead, show high-level cards:

Total Vulnerabilities
Planned
Unplanned

Confirmed:

Remediation Planned Date blank
-> Unplanned

A record with a valid Remediation Planned Date is part of Planned.

Keep individual Quarter and Month information in the chart and summary table.

==================================================
5. BUSINESS FUNCTION FILTER
==================================================

Keep raw and mapped Business Function semantically separate.

If filtering the original source field, label the filter:

Business Function

If filtering the standardized:

IVS
AVS
CVE
PT

classification, label the filter:

Mapped Business Function

Do NOT call the standardized four-category field "Business Function" because
that would make it unclear whether the user is filtering raw or processed data.

==================================================
6. DATA-AS-OF INFORMATION
==================================================

Continue displaying:

Data as of <Report End Date>

Example:

Data as of 31 Aug 2026

Do NOT hardcode the date.

Retrieve it from processing-run metadata.

Also display the relevant processed source filename where appropriate.

==================================================
7. REPORTING PERIOD / PROCESSING RUN
==================================================

The latest completed processing run should remain the default.

However, design the page so historical reporting periods can later be selected.

Conceptually:

Reporting Period
[ August 2026 ▼ ]

When historical runs exist, users should eventually be able to switch between
them without uploading the file again.

Do not implement artificial historical periods if only one processing run
currently exists.

==================================================
8. ACTIVE FILTER SUMMARY
==================================================

Add a compact active-filter summary.

Example:

Active Filters:

ICS Hierarchy: Wealth and Retail Banking
Within SLA?: No
Remediation Status: Open, In Progress

If no filters are active:

All applicable records

Allow individual active filters to be removed easily.

Also retain:

Reset Filters

This is important so screenshots and exported reports clearly show what data
the user is looking at.

==================================================
9. FILTER BEHAVIOR
==================================================

Filters should:

- Support multiple selections where appropriate
- Display "All" when nothing is selected
- Display the selected value for one selection
- Display "2 selected", etc. for multiple selections
- Update the report without full page reload
- Update KPIs
- Update charts
- Update distributions
- Update summary tables
- Update Grand Total

Avoid triggering different calculations between the chart and table.

All visualization components on the page must use the SAME filtered report
population.

==================================================
10. FILTER OPTION COUNTS
==================================================

Where practical, display the available count next to filter values.

Example:

Remediation Status

Open (125)
In Progress (86)
Closed (210)

The count should reflect the appropriate current filter context.

Do not implement this if it makes filter performance poor for large reporting
runs.

This is a usability enhancement, not a required business rule.

13. CHART DESIGN

Keep charts complementary to the table rather than duplicating everything.

==================================================
15. TABLE/CHART INTERACTION
==================================================

Where practical, allow a chart segment to act as a filter/drill-down shortcut.

Example:

User selects:

North Asia/P2 table cell.

Do not create different definitions between chart clicks and table clicks.

Both must use the same reporting filters.

==================================================
16. DRILL-DOWN
==================================================

Keep click-to-drill-down.

Clicking a summary cell must open ONLY the records represented by that exact
cell.

Example:

Current filters:
ICS Hierarchy = Wealth and Retail Banking

Clicked:
North Asia -> P2

Drill-down must inherit:

- Current page filters
- North Asia row condition
- P2 column condition

Do not show records outside the selected summary population.

18. DRILL-DOWN PAGINATION
==================================================

==================================================
19. DISTINCT COUNT
==================================================

This rule is critical.

Every displayed vulnerability count is:

DISTINCT COUNT of Unique Reference ID

This includes:

- KPI cards
- chart segments
- distribution counts
- table cells
- row subtotals
- column subtotals
- Quarter totals
- Grand Total

Calculate each total independently.

Do NOT create Grand Total by simply adding displayed child cells.

The same Unique Reference ID may occur in more than one child grouping.

Records without a usable Unique Reference ID must not artificially increase
the vulnerability count.

Add a small Data Quality indicator to the report header or near the report
metadata.

For example:

Data Quality
12 warnings

Do NOT treat data-quality warnings as vulnerabilities.

This is informational so a user can understand whether mappings, IDs or input
values require review.

Possible existing issues can include:

Missing Unique Reference ID
Duplicate Unique Reference ID
Check Mapping
Unmapped Business Function
Invalid Date
Check Input

Only display issues that actually exist for the selected processing run.

21. SOURCE VS CALCULATED FIELD CLARITY

==================================================
22. EMPTY STATES
==================================================

Handle no-result filters gracefully.

If the selected filters produce zero vulnerability records, do NOT show a
broken or misleading empty chart.

Display something such as:

"No vulnerabilities match the selected filters."

Still show:

Active Filters
Reset Filters

Do not present zero rows as an application error.

==================================================
23. LOADING STATES
==================================================

When summary data is being fetched:

- Do not display stale numbers as though they belong to the new selection.
- Show appropriate loading/skeleton states.
- Prevent duplicate requests where practical.

Do not block navigation unnecessarily.

==================================================
24. ERROR STATES
==================================================

If the reporting API fails, show a clear report error state.

Do not expose backend stack traces in the UI.

Provide a safe retry action where supported by the existing architecture.

==================================================
25. EXPORT CURRENT VIEW
==================================================

Design the reporting interface so the CURRENT filtered summary can eventually
be exported.

The exported summary should represent:

- Current report type
- Reporting period
- Active filters
- Rows
- Columns
- Distinct vulnerability counts

Do not automatically export the entire underlying raw dataset when the user
only requests a summary.

If export functionality is not currently implemented, keep this as a planned
enhancement rather than blocking the current report implementation.

==================================================
27. PROCESSING-RUN TRACEABILITY
==================================================

Every displayed summary must be tied to one completed processing run.

Metadata should make it possible to determine:

- Reporting period
- Processed filename
- Processing run
- Data-as-of date

Do not combine records from different reporting runs unless a future
cross-period report explicitly requests it.

==================================================
28. PERFORMANCE
==================================================

Current in-memory aggregation is acceptable for the synthetic prototype.

However, do not make loading an entire large reporting run into application
memory a permanent architectural requirement.

Keep the reporting service modular so filtering/aggregation can later move to
PostgreSQL or another approved scalable implementation.

Do NOT send the complete reporting dataset to React for client-side
PivotTable calculations.

React should receive aggregated summary results.

Drill-down records should be loaded separately and paginated.

==================================================
29. RESPONSIVE DESIGN
==================================================

Preserve the current desktop corporate-dashboard experience.

For narrower screens:

- KPI cards may wrap
- Filters may stack
- Tables may scroll horizontally

Do NOT squash the Pivot-style summary table until column labels become
unreadable.

Desktop screenshots remain the main presentation target for the university
project.

==================================================
30. SUMMARY VIEW PRINCIPLE
==================================================

The final interface should feel like a web-based improvement over the existing
Excel reporting workflow, NOT an Excel PivotTable copied directly into a
browser.

Preserve:

- Familiar Cluster/Country hierarchy
- Familiar filters
- Familiar reporting categories
- Exact business calculations

Improve:

- Navigation
- Filtering
- Expand/collapse
- Visualization
- Drill-down
- Data-quality visibility
- Historical run selection
- Readability
- Traceability

Do not add features that require new, unconfirmed business rules.

Do not redesign currently working functionality unnecessarily.
