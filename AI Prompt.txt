# Task: Create a CISO Reporting Business Rule Flowchart

I am working on a **Vulnerability Management Reporting Automation System** for my internship project.

I need you to create a professional business rule flowchart titled:

# CISO Reporting Business Rule Flow

The purpose of this flowchart is to show how the CISO vulnerability report is prepared, starting from obtaining the latest MI.23 and MI.24 data, updating remediation information, producing MI summaries, and finally updating the historical data and Burndown report.

---

## 1. Data Sources

The process starts by obtaining the following data:

1. Latest MI.23 data from MSTR
2. Latest MI.24 data from MSTR
3. Latest PT Tracker from the Technology Team
4. Latest CVE/SPM data from MSTR

MI.23 and MI.24 must be maintained as separate datasets.

---

## 2. MI Classification Business Rule

### MI.23

MI.23 represents:

- Overdue findings
- High severity
- Critical severity

Represent this business rule as:

`Overdue AND Severity = High/Critical → MI.23`

### MI.24

MI.24 represents:

- Medium severity findings

Represent this as:

`Severity = Medium → MI.24`

---

## 3. Prepare MI.23 and MI.24 Data

For both MI.23 and MI.24 datasets, add/populate these four reporting columns:

1. Within SLA?
2. Updated Remediation Status
3. Updated Planned Remediation Month
4. Updated Planned Remediation Date

Both MI.23 and MI.24 should pass through the same enrichment/business-rule process.

---

## 4. Business Rule: Within SLA?

Use:

- Report Week End Date
- SLA Due Date

Decision logic:

### Is SLA Due Date available?

**No**
→ Set `Within SLA? = No SLA`

**Yes**
→ Compare Report Week End Date with SLA Due Date.

### Is Report Week End Date <= SLA Due Date?

**Yes**
→ Set `Within SLA? = Yes`

**No**
→ Set `Within SLA? = No`

Represent this clearly as decision diamonds.

---

## 5. Business Rule: Determine PT or CVE/SPM

After calculating SLA status, determine the vulnerability/remediation source.

Decision:

`Is the record PT or CVE/SPM?`

Create two separate branches.

---

## 6. PT Branch

For PT records:

### Match

Use:

`Unique Reference ID`

to search the latest PT Tracker.

The latest PT Tracker is used to obtain:

- Latest Remediation Status
- Latest Remediation Planned Date

### Updated Remediation Status Rule

Decision:

`Is latest PT Remediation Status available?`

**Yes**
→ Use the latest PT Remediation Status

**No**
→ Retain the existing Remediation Status from the MI dataset

---

## 7. CVE/SPM Branch

For CVE/SPM records:

Use the latest CVE/SPM data from MSTR.

Use the required matching key.

Where required, matching uses:

`Unique Reference ID + Hostname`

Use the matched CVE/SPM record to obtain the latest remediation information.

### Updated Remediation Status Rule

Decision:

`Is latest CVE/SPM Remediation Status available?`

**Yes**
→ Use latest CVE/SPM Remediation Status

**No**
→ Retain existing Remediation Status from the MI dataset

---

## 8. Business Rule: Updated Planned Remediation Date

For both PT and CVE/SPM, determine the final planned remediation date.

### Decision 1

`Is a valid latest Remediation Planned Date available?`

**Yes**
→ Use the latest Remediation Planned Date

**No**
→ Check the existing MI Remediation Planned Date

### Decision 2

`Is an existing Remediation Planned Date available?`

**Yes**
→ Retain the existing Remediation Planned Date

**No**
→ Set:

`Updated Planned Remediation Date = No Plan Date`

The resulting value becomes the final Updated Planned Remediation Date.

---

## 9. Business Rule: Updated Planned Remediation Month

Use the final Updated Planned Remediation Date.

If a valid date exists:

`Updated Planned Remediation Date → Convert to reporting month`

Examples:

- 30-Sep-2026 → 2026-9
- 31-Oct-2026 → 2026-10
- 30-Nov-2026 → 2026-11
- 31-Mar-2027 → 2027-3

If:

`Updated Planned Remediation Date = No Plan Date`

then:

`Updated Planned Remediation Month = No Plan Date`

---

## 10. Four Final Reporting Fields

At this point, every relevant MI.23 and MI.24 record should have:

- Within SLA?
- Updated Remediation Status
- Updated Planned Remediation Month
- Updated Planned Remediation Date

Once these four fields have been prepared, proceed to report summarisation.

---

## 11. Generate MI Summaries

Create two separate summary paths:

`Completed MI.23 Data → MI.23 Summary`

`Completed MI.24 Data → MI.24 Summary`

The summaries aggregate the detailed vulnerability data into reporting-level information.

The flowchart should show the two datasets separately before combining them at the CISO reporting level.

---

## 12. CISO Management Summary

Use the MI.23 and MI.24 summary results to support the CISO management-level report.

The management summary includes information such as:

- Application Name
- Overdue
- Exception
- Total
- Planned Remediation By
- Risk Assessed
- Remediation Progress

Represent this as:

`MI.23 Summary + MI.24 Summary → CISO MI Summary`

---

## 13. Historical Data 2026

The reporting process also maintains historical MI information.

After the current MI.23 and MI.24 results are completed, store the required reporting-period results in:

`Historical Data 2026`

Historical Data 2026 maintains previous reporting-period information so that vulnerability movement can be tracked over time.

Represent this relationship as:

`Current MI.23 / MI.24 Results → Historical Data 2026`

---

## 14. Burndown Business Rule

The Burndown report should NOT directly read the raw MI.23 or MI.24 datasets.

Its data source is:

`Historical Data 2026`

Represent the relationship clearly as:

`MI.23 / MI.24 Results → Historical Data 2026 → Burndown`

The Burndown uses the historical reporting information to show vulnerability movement across reporting periods.

# Flowchart Design Requirements

Create the flowchart using standard flowchart notation:

- **Oval** → Start / End
- **Rectangle** → Process
- **Diamond** → Business rule / decision
- **Cylinder** → Data source or historical data storage
- **Arrows** → Process flow

Use a professional and clean visual style suitable for a university internship project report.

## Layout Requirements

- Use a top-to-bottom layout.
- Keep MI.23 and MI.24 visually separate where appropriate.
- Clearly separate PT and CVE/SPM processing branches.
- Clearly label all Yes/No branches.
- Merge PT and CVE/SPM flows after their lookup/update processes are completed.
- Clearly distinguish between input data, calculations, decisions, summaries, and outputs.
- Show Historical Data 2026 as the source for the Burndown.
- Avoid overcrowding the diagram.
- Do not place long Excel formulas inside flowchart boxes.
- Use short, clear business terminology.
- Do not invent additional business rules.
- Do not change the supplied business logic.
